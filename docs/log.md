# Log

## 2026-08-11

* **Creation**: `define-scope/references/checklist-brownfield.md` — a second enumeration floor, for a scoping run on a system that already shipped. The single checklist is greenfield by construction, and four of its eleven areas have no honest brownfield answer: "what pain does this solve", "who is v1 for", "what does the user receive", "what are the core journeys" all come back *already decided*, so the ledger dutifully emits four `status: na` docs carrying no information and the whole run reads as filler. Those four are not *absent* on an existing product, they are different questions — what the next phase solves that the shipped thing doesn't, which existing users it serves and which it disturbs, whether it changes what the user receives at all, which live flows it touches and what breaks — which is why this is a sibling file rather than a collapse of the four into one doc: collapsing buys tidiness at the price of never asking them at all. The remaining areas are rewritten where the shape changes (the cut ships into a system with live users, so too big to finish is also too big to roll back; non-goals guard against the adjacent cleanup the code invites rather than the tempting deferred feature; success criteria have a measured baseline to be a delta against, which makes "no regression in X" a legitimate verdict) and left alone in a clause where it doesn't. Three areas exist only here — what the shipped system already decides, what must not break, migration of existing users and data — each capped at scoping altitude on purpose, because the file-level blast radius is `define-change`'s impact audit, read out of the code rather than asked of the user, and a ledger that reaches for it wastes the user's attention on facts. **The routing half is deliberately absent**: which checklist a run uses is answered nowhere, and the only path to the sibling is the user saying the project is already shipped, taken at face value in Step 1 with no signal inspected. Detection logic bolted into `define-scope` is exactly the failure the missing guide skill ([#21](https://github.com/julienlegoux/skills/issues/21)) exists to prevent — every skill patching its own entry conditions, one `if` at a time, drifting immediately — so that half waits on it, and both checklists say so in their headers where a later reader would otherwise mistake the one affordance for the answer. Reported as [issue #11](https://github.com/julienlegoux/skills/issues/11).
* **Creation**: `_shared/feedback-interfaces.md` — a fifth contract under `skills/_shared/`, and the first that governs nothing written to disk. Skills learn things about themselves during a run — a step that reads wrong, an instruction the user has to correct twice — and nothing carried the lesson out of the session that paid for it: `define-conventions` Step 4 did it for exactly one category (a baseline promotion the user's own words revealed as non-project-specific) and every other skill dropped it on the floor, which is how the same misfire gets rediscovered by the next user instead of fixed once. The contract generalizes that reflex: it fires once, at the end of a run, after the deliverable is reported — never mid-run — and only on something that clears two filters, attribution (the skill caused it, or could have worked around it; not an outage, not a wrong command, not a tool bug) and generality (true on any project, not "our monorepo has an odd layout"). Both must hold, and when nothing does the run ends **silently** — no offer, no "anything to report?" — because a skill that asks after every run trains the user to answer no without reading, and the reflex is then worth nothing on the day it has something to say. Routing is [#14](https://github.com/julienlegoux/skills/issues/14)'s rule promoted: `improve-skill` when a clone is at hand and the fix is happening now, `send-feedback` otherwise, with the discriminator explicitly *not* "does the user have a clone" — the session that reported this had one and still wanted the lesson recorded upstream rather than fixed on the spot. Its own file rather than a section of `bundle-interfaces.md`, because nothing here concerns writing under `docs/` and the audience is the larger set: defined as **every skill under `skills/` except `send-feedback`** — 17 today, but stated as a rule, since a count goes stale the next time a skill is created. `send-feedback` is the exclusion because it is the destination, and a run of it ending by proposing feedback about itself is a loop with no floor. `meta/` stays out for a structural reason rather than a judgment call: meta-skills resolve no `skills/_shared/` path at all, and the routing half has a constant answer there anyway, since a clone and push rights are their entry condition. The *obligation* lives in `meta/_shared/authoring-interfaces.md`, so a skill written tomorrow inherits the pointer instead of the reflex being remembered per skill until it isn't. `define-conventions` keeps its promotion check — its destination is `assets/baseline.md` rather than an issue, which is a genuinely local category — but stops restating the routing rule and names the contract instead. Reported as [issue #16](https://github.com/julienlegoux/skills/issues/16), with [#14](https://github.com/julienlegoux/skills/issues/14) as its first instance.
* **Update**: `_shared/ledger-interfaces.md` now carries the ledger's *procedure* — a `Triage — the batch pass` section and a `Deep-dive` section — not just the decision doc schema. The two passes were written out five times, once per ledger skill, and `define-change` Step 4 opened with "Same as define-scope's Step 3", which is duplication admitting itself. Five copies drift, and they had: the rule that a self-excluded list gets its own explicit confirmation existed only in `define-scope`, so an "accept all" in `define-specs` or `define-change` silently swallowed every N/A those skills produced — the exact incident `define-scope` documents in its own rationale, three core pillars auto-N/A'd in one session, latent in two more skills. Centralizing propagates that guard, and with it the A/B/C rule that was local to `define-conventions` (conversational assent is not a verdict) and the terseness rule that was local to `define-scope`. It also gives the "never `AskUserQuestion` at triage" rule a place to live at last: the tool cannot express "accept all except 3 and 7", and it flattens a free-form answer into whichever option sits nearest, which on a ledger is a verdict the user never gave. Deliberately two sections rather than one: a batch round-trip and a waiting sequence are different interactions. `define-concept` keeps its own copy of the `AskUserQuestion` ban — it has no ledger, does not read this contract, and is the most conversational skill in the repo. Reported as [issue #12](https://github.com/julienlegoux/skills/issues/12).
* **Update**: `_shared/bundle-interfaces.md` prescribes `git commit -F <file>` for any message longer than one line. Every skill in the pipeline commits, but the mechanism for getting the message *text* into git was never specified, so the model picked a quoting strategy per run — and on a machine exposing both PowerShell and Bash it can pick one the other shell mangles. A PowerShell here-string executed by bash is read as three adjacent tokens and concatenated, planting the `@` delimiters as the message's first and last lines; git accepts it, the commit pushes, and history is append-only, so the corruption is found days later in the log. `-F` has no quoting surface in any shell, which is what makes it the mechanism rather than one option among several. Reported as [issue #13](https://github.com/julienlegoux/skills/issues/13).
* **Update**: Epics got a terminal status. The schema stopped at `draft | open` — issues run to `done`, epics had nowhere to land — so `close-epic` could not close an epic's own status *even in principle*. A run over three finished epics flipped 27 issues to `done`, closed every GitHub issue and all three milestones, and left all three `EPIC_N.md` files, plus their bullets in the epics bundle root `index.md`, reading `open`. That index is the one surface a later reader scans for where the project stands. `status: done` now exists in `_shared/pipeline-interfaces.md`, and `close-epic` writes it with the index bullet in the same step that closes the milestone, under the same condition. Reported as [issue #10](https://github.com/julienlegoux/skills/issues/10). Note the interaction with the `epic: 0` lane below: closing an epic and *retiring* one are different verbs, and [issue #22](https://github.com/julienlegoux/skills/issues/22) is where that gets settled.
* **Update**: `implement-epic` renders its progress board during the run — when a frontier is spawned, and after each merge — instead of only at the end. Step 1 already built the board and the loop already kept it current; nothing ever said to *show* it, so the only user-visible artifact the skill prescribed was the final report, arriving when a multi-hour run was already over. The columns are the ones the supervisor holds anyway, so there is no extra reading and no context growth, and the final report's **Models used** line becomes a running total rather than a recollection. Reported as [issue #18](https://github.com/julienlegoux/skills/issues/18).
* **Update**: Retiring epic 0 moved from `triage-reports` to `close-epic`. `triage-reports` is invoked when review reports pile up, not when an epic finishes implementing, so the skill that owned the lane's disposal was never loaded at the moment disposal became due — the folder lingered for a whole cycle, and its bullet sat in the epics index claiming live remediation work. `close-epic` is running at exactly that moment and has already established the precondition retirement needs. It now removes the folder, drops the bullet, and writes the retirement notice, under the same grouped confirmation as the worktree and branch cleanup. Two consequences worth naming: epic 0 never takes the new `status: done` — it is *retired*, not closed, because zero is a slot the next triage cycle needs back rather than an identity worth keeping — and anything linking into the folder is repointed at GitHub before it goes, including the `Evidence` field of any drift promoted out of it moments earlier, since both logs are append-only and a dead link there stays dead. Reported as [issue #22](https://github.com/julienlegoux/skills/issues/22). Plugin `0.5.0` → `0.5.1`.

## 2026-08-09

* **Creation**: `triage-reports` — the converter the review family was missing. A review never repairs what it reviews, which is what keeps its report trustworthy; the cost is that findings pile up in `docs/REPORT_<n>.md` with nothing that turns them into work. Found the hard way on a real series: nine `review-issues` reports, 97 findings, 0 P0, and no path from them to anything anyone could implement. Its centre is **grouping by repair rather than by finding** — the same defect recurs across reports because the reviewers looked at nine artifacts built the same way, so one wrong link form in nine `issues/index.md` files is one repair, not nine. Ninety-seven findings collapse to roughly ten issues; one per finding would have been unusable. One skill covers both flavours: which one a report is comes from its `## Scope`, never a flag, and a mixed series yields one epic with plan repairs before code fixes, since repairing an issue changes the contract the code will be judged against.
* **Update**: `epic: 0` is now reserved in `pipeline-interfaces.md` for the remediation lane. Every other epic number is a position in the planned build order; zero means *before continuing*, which reads identically from either direction — plan repairs before the epics they repair get implemented, code fixes before the next epic builds on them. Temporary and single-owner: `triage-reports` creates it, extends it while it is in flight rather than opening a second, and retires the folder once it is empty. The retirement notice in `docs/epics/log.md` survives it, carrying which reports were consumed and what they produced — which is also how the next run avoids re-triaging findings it already fixed. The folder can go; the memory can't.
* **Update**: `review-implementation` keeps deciding dispositions — `accept` means the *standard* is wrong, and only the reviewer holds the context for that call — but stops creating follow-up issues. A `fix-now` fixed alone, while its four siblings from the same root cause sit in three other reports, is the duplication that skill exists to catch. It records the disposition; `triage-reports` converts it, and honours it rather than re-triaging.
* **Update**: `_shared/review-interfaces.md` names `triage-reports` as what turns findings into work, covering both planning reviewers in one edit instead of two. Its audience in [Shared interfaces](shared-interfaces.md) now includes the reading end of the report contract.
* **Update**: [The idea-to-PR pipeline](pipeline.md), [Repo architecture](repo-architecture.md) — the fourth review companion and the epic 0 lane. Plugin `0.4.0` → `0.5.0`.

## 2026-08-08

* **Creation**: `define-concept` — the stage upstream of `define-scope`, closing the gap [issue #8](https://github.com/julienlegoux/skills/issues/8) reported: nothing owned the phase where an idea is still becoming a product, so it ran ad-hoc and handed `define-scope` artifacts no contract governed. Written from the four sessions that actually produced one, and shaped against them: no ledger, no checklist, no numbered steps, because the phase is a conversation and structure is what kills it. What is hard is only the record — nothing lands on disk until the user validates it, `log.md` carries the rationale a ledger would have held, and `CONCEPT.md`'s headings are emergent rather than templated. Optional by design; a clear idea still goes straight to `define-scope`. Plugin `0.3.0` → `0.4.0`.
* **Update**: `define-concept` writes into `docs/planning/`, not a bundle of its own. The ad-hoc run had made `docs/` a bundle root, which stopped the tree validating the moment `docs/planning/` claimed its own — OKF v0.1 has no nested bundles. A sibling `docs/product/` would have worked around it; one bundle for everything preceding code removes the collision instead, keeps the project's whole planning history on a single timeline, and leaves `bundle-interfaces.md` untouched at two bundles.
* **Update**: `define-scope` reads `CONCEPT.md` and `DOMAIN.md` as settled intake rather than a draft to re-decide, and its description now carves the boundary both directions — CONCEPT answers "is this the right thing to build?", SCOPE answers "what is its first version?". Its project-home offer also stands down when the concept doc sits in a repo-less folder, which means the offer was already made and declined.
* **Creation**: `_shared/review-interfaces.md` — a fifth shared contract, for `review-epics` and `review-issues`. The two skills had been written outside this repo's conventions: they restated the OKF, schema and GitHub rules inline instead of pointing at `_shared/`, and carried a verbatim copy of each other's severity scale, report template and GitHub policy. Restating a contract is how it drifts — the whole reason `_shared/` exists — and it had already happened here. The contract now holds what a review *is*: grading by user impact, a finding that names both sides or is only an opinion, GitHub as corroboration rather than subject, and the `REPORT_<n>` series (shared with `review-implementation`, which grades code against yardsticks of its own and stays out of this audience).
* **Update**: The two planning reviewers delegate their analysis pass to a model outside the Claude family when `opencode` is on `PATH`, run read-only (`--agent plan`) against the repo, with the model matched to the weight of the review and large surfaces batched by area. A reviewer that did not write the thing is not re-reading its own reasoning, which is where a self-review is weakest. Capability-detected on purpose: absent the tool the review runs natively and says nothing, since a skill that advertises tooling the user never asked for is noise. What comes back are leads to verify against the files — an external session has no memory of how these artifacts were produced and will read a deliberate convention as a defect.
* **Deprecation**: Deleted `review-epics/agents/openai.yaml` and `review-issues/agents/openai.yaml` — Codex interface stubs left over from authoring those two skills elsewhere. Nothing in this repo reads them, `agents/` here means Claude Code subagent definitions, and their `default_prompt` still pointed at `docs/PLAN.md`, superseded by `docs/planning/SCOPE.md`.
* **Creation**: `close-epic` — the seam after `implement-epic`'s loop stops. A stopped run is not a closed epic: worktrees still on disk, merged branches still on the remote, the milestone still open, and what the implementers learned still in a chat report that dies with the session. It verifies the epic's real state against GitHub and git, promotes the drift records into the register, closes the milestone, and cleans up.
* **Creation**: `review-implementation` — reviews the code an epic actually shipped, against the acceptance criteria, `CONVENTIONS.md` and the accepted drift. Every PR in an epic was reviewed alone and passed alone, which is the problem: duplication across issues, an abstraction several implementers each re-invented, a convention eroding a little per PR — none of it visible from inside a single PR, all of it merged by the time anyone could look.
* **Creation**: `send-feedback` — the return path for people who installed the plugin and have no clone to fix anything in. Files an issue on this repo with the user's words quoted verbatim (paraphrase is what destroys the subtle feedback), context offered rather than assumed, private paths redacted, nothing posted without explicit approval. Works for anyone: the repo is public with issues open, so `gh` handles it when authenticated and a prefilled issue-form URL when not — no token bundled, no proxy. Labels degrade gracefully, since a non-collaborator cannot apply them.
* **Update**: The deviation register became the **drift register**, one vocabulary end to end. "Deviation" was already taken: in `define-conventions` it is a decided divergence from the personal baseline — it *is* the project's standard. Drift runs the opposite direction, discovered after the fact against that standard. Two artifacts, two jobs: per-epic drift records written by `implement-issue` as evidence, promoted once by `close-epic` into `docs/planning/DRIFT.md`, the single-writer surface every later run reads beside `SPECS.md` and `CONVENTIONS.md`.
* **Update**: [The idea-to-PR pipeline](pipeline.md), [Repo architecture](repo-architecture.md), [Shared interfaces](shared-interfaces.md) — documented the three new skills and the drift register, the one contract in the pipeline that flows backwards. Found by linting this bundle against the repo: the docs described a pipeline that ended at a merged PR.
* **Update**: `.github/ISSUE_TEMPLATE/feedback.yml` + `config.yml` — the receiving end of `send-feedback`. Blank issues stay enabled on purpose: the skill's long-body fallback needs the plain `?title=&body=` URL to resolve. Plugin `0.2.0` → `0.3.0`.
